# Release transport: integration and verification

The transport ships in the standard Release configuration and is wired to the existing LAN tab. The application itself has not been run by the development tests. Multicast discovery has an isolated test group; the autonomous controller harness binds TCP only to loopback with an explicitly test-only route override.

- `TlsChannel`: Schannel TLS 1.2 (ECDHE/ECDSA with AES-GCM), fresh server certificate, automatic reconnect disabled. Compare the entire 96-bit `tls-unique` code on both PCs; confirm locally on each only if it matches. Then compare the full embedded `ANTIZAPRET_VERSION` and LAN protocol revision byte-for-byte. No fallback for old framing. After that, one compatible operation may begin. The temporary server key is a named, non-exportable current-user CNG key and is deleted on normal object teardown. Forced process exit may leave this key behind; no trust store is changed.
- `Send` / `Receive`: after the recipient selects an existing local NTFS folder, matching files are grouped by size and SHA-256. The recipient selects replacements before file contents are sent. Selected files are staged and verified before being moved into place; skipped files and paths absent from the manifest are left alone. A crash or failed rollback can leave a `.AntiZapret-LAN-*.tmp` file, including a backup of an original. A missing receipt after the final marker means the sender cannot tell whether the receiver saved; do not retry silently. Limits: 16,384 entries, 64 GiB offered, 16 relative path segments. Disk space is checked against the selected data; it is not reserved.
- `RequestSpeed` / `AnswerSpeed`: explicit consent; up to 16 MiB per direction, sent sequentially, 10 s per direction, 30 s to answer. No test files; cancelled or timed-out test reports no measurement. Display payload bytes divided by measured receive duration. Upload duration comes from the peer's receive clock; the result is encrypted-session throughput, not Wi-Fi link speed.

## Release admission and UI

Both users must keep the LAN tab open and enable Visibility. A client running only legacy discovery can still appear on the card but has no eligible transport route. Active opted-in discovery binds the peer identity to its observed on-link source, the local address and the interface; a stale, missing or ambiguous route cannot start an exchange. Addressed invitations include a fresh receiver challenge and a one-time ticket. The receiver starts an exclusive TCP listener only for a valid pending invitation. The port is derived from the locally generated invitation, not an arbitrary advertised endpoint. Workers check the actual on-link Windows Private route, physical Ethernet/Wi-Fi and strong-host settings at setup and periodically during the operation. TCP is bound to the selected address/interface; exact connection endpoints, TLS comparison, compatibility revision 2 and the invitation ticket are checked before application metadata or payload. No firewall rule is set. If current firewall policy blocks TCP, the operation fails rather than trying a different destination or bypass.

The existing discovery tick uses non-blocking multicast; TCP, TLS, waiting for decisions and file I/O run on the worker. One pending/active exchange is allowed. Leaving the tab, turning off local visibility, or losing the fresh route stops the exchange. Both users compare the full code and confirm; the recipient separately approves a speed test or a file offer. File acceptance requires choosing an existing local NTFS folder. Revision 4 checks that folder before sending file contents. In the conflict dialog, applying the decision to all affects only the current group (identical or different). The outgoing manifest contains only checked entries plus missing directory ancestors, never unchecked descendants solely because a parent is checked.

On two physical PCs (not covered by the autonomous tests), check appearance of both cards, exact code comparison, separate acceptance/decline, speed in both directions, a partially checked tree, chosen-folder receipt, and cancellation after leaving the tab. Test against the existing Windows firewall policy without changing it.

## Standalone Windows test

From the repository root in an x86 Visual Studio Developer Command Prompt (put output in an isolated scratch directory):

```bat
cl /nologo /EHsc /std:c++17 /utf-8 /W4 /WX /DUNICODE /D_UNICODE /DANTIZAPRET_LAN /DANTIZAPRET_LAN_TEST /Isource\AntiZapret /Fo"%TEMP%\\" /Fe"%TEMP%\az-lan-transfer-test.exe" source\AntiZapret\lan\lan_transfer_tls.cpp source\AntiZapret\lan\lan_transfer.cpp source\AntiZapret\lan\lan_speed.cpp tests\lan_transfer_test.cpp
```

Run the executable with an existing writable local NTFS scratch directory as its first argument. Optionally provide a junction you created inside that scratch directory as the second argument to test rejection of an actual reparse point. A deliberately stalled speed direction takes about 10 seconds to test. The harness defines `ANTIZAPRET_LAN_TEST` only for version injection and legacy framing; never enable it in a release build.

The controller harness in `tests/lan_session_test.cpp` uses the same compiler flags. Link `lan_session.cpp`, `lan_discovery.cpp`, `lan_transfer_tls.cpp`, `lan_transfer.cpp`, and `lan_speed.cpp`, plus `Ws2_32.lib Bcrypt.lib Iphlpapi.lib Ole32.lib Shell32.lib`. Pass an existing local NTFS scratch folder. The discovery harness `tests/lan_discovery_test.cpp` links `lan_discovery.cpp` plus `Ws2_32.lib Bcrypt.lib Iphlpapi.lib Ole32.lib`; it requires an already-Private eligible adapter and does not change its profile.
